# 错峰分析、定时推送与可配置变量

## arXiv 什么时候发布

arXiv 通常在**美东周日至周四 20:00**发布新批次，北京时间对应**周一至周五夏令时 08:00、冬令时 09:00**；节假日或临时原因可能延期。[arXiv 官方发布表](https://info.arxiv.org/help/availability.html)。

Hugging Face Daily Papers 是精选来源，不保证与 arXiv 同时收录。希望尽早发现当天论文，应同时启用 `ARXIV_ENABLED` 并设置英文关键词；HF 可以补充社区精选及票数。候选上限、关键词覆盖和来源本身都有范围限制，不能承诺不漏任何论文。

## 当前时间安排

默认 `LLM_OFFPEAK_ONLY=true`：分析优先在谷时进行，用更低的 token 成本；投递已生成日报不调用模型，任何时段都能发。GitHub 定时触发本身不保证准点，所以默认不追高峰价格。

| 时期 | arXiv 通常发布时间（北京） | 低峰分析时间（北京） | 典型送达 |
| --- | --- | --- | --- |
| 夏令时 | 08:00 | 08:10–08:50 | 09:30 |
| 冬令时 | 09:00 | 12:17 起 | 12:17 之后；设 `ARXIV_FRESHNESS_PRIORITY=true` 可 09:10 开始、09:30 送达 |

冬令时 09:10 落在默认高峰窗口（09:00–12:00）内。想把冬令时日报提到上午，设 `ARXIV_FRESHNESS_PRIORITY=true`，允许 09:10–10:30 的高峰例外，费用按高峰计。想让全年都按时优先，设 `LLM_OFFPEAK_ONLY=false`，代价是定时分析可能按高峰价格计费。

夏冬令时都以北京时间 09:30 为主推送时间，不使用外部调度服务。夏令时 08:10 开始分析，通常在 09:00 前完成；如果分析跨过 09:00，会在 12:17 继续并在完成后补发。GitHub 调度延迟、来源获取和模型耗时仍可能使日报晚于 09:30；定时分析完成时若已过目标时间，会立即补发，不承诺严格准点。

每天成功完成一个定时批次并把结果写入仓库的artifact；同一工作流根据状态恢复分析或投递，**即使推送时处于高峰，也不会再次调用 LLM**。重试保留成功单篇的分析缓存；修改模型、提示词或输入后会重新分析。未完成分析不会被当成成功日报推送，也不会绕过计费保护补生成。当天零篇同样记录完成，避免每次检查重复抓取。手动 `all`、`reissue` 是显式操作，不受当天完成标记限制。

`--analyze-only` 只生成正式待发批次，`--publish-only` 只发送。分析成功不会立刻提交“已推送”记录，群与文档目标成功后才提交。已有待发批次时分析任务会恢复它，不覆盖成另一份日报。

## 时间在哪里改

GitHub的 `on.schedule` 不支持从Repository Variables动态插入cron，所有触发表达式集中在 `.github/workflows/daily.yml`，明确使用UTC：

| UTC cron | 北京时间 | 用途 |
| --- | --- | --- |
| `10,25,40,55 0-3 * * *` | 08:10–11:55，每15分钟 | 恢复未完成分析或投递；只有处于低峰窗口时才启动分析 |
| `30 1 * * *` | 09:30 | 主推送检查 |
| `17 4,10 * * *` | 12:17、18:17 | 允许的低峰时段补分析、补投递 |

定时检查与手动操作统一在 `.github/workflows/daily.yml`，`workflow_dispatch` 提供 `analyze` 入口。19次检查不代表19次模型分析；成功完成当天批次后，后续检查直接退出，但仍消耗少量Actions运行时间与artifact存储。私有仓库应留意Actions用量。

统一入口 `tick`先恢复artifact中的批次、单篇缓存、回执和 `schedule.json` 当天完成标记。已生成日报等待目标时间；缺少分析时才在价格规则允许的时段启动或恢复。过期日报仍会报错，不覆盖旧批次或悄悄改为当天日期。所有定时、手动任务共用串行锁。日志显示实际UTC时间、北京时间和触发cron，方便分辨未触发、排队和处理失败。

修改推送时间时，同时调整 `PUBLISH_TIME_BEIJING`、主触发UTC cron及检查时段。仅改Variable不会改变GitHub触发时间。修改提交到默认分支后生效。多次检查仍依赖GitHub实际触发；不承诺严格准点。[GitHub调度说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。

## 低峰价格保护 Variables

**省钱优先（默认）：** `LLM_OFFPEAK_ONLY` 未填写时按 `true` 处理。定时分析、PDF 机构识别与失败恢复只在 `LLM_PEAK_WINDOWS` 之外调用模型；已生成的日报仍可在任意时段投递。GitHub 定时触发本来不保证准点，默认让分析跟随谷时，避开高峰价格。代价是冬令时首轮分析等到 12:17，日报送达时间随之后移。

**按时优先（可选）：** 将仓库 Variable `LLM_OFFPEAK_ONLY` 设为 `false`，允许定时分析在任何时段调用模型，费用按服务商实际规则计。这样夏冬令时都不会因为低峰保护等待到中午或晚上；`PUBLISH_TIME_BEIJING` 仍控制已生成日报的最早自动投递时间。这个设置只解决模型计费时段限制，不能消除 GitHub 定时事件延迟。

以下均在 **Settings → Secrets and variables → Actions → Variables** 中填写。未填采用表中默认值。

| 变量 | 默认值 | 作用 |
| --- | --- | --- |
| `PUBLISH_TIME_BEIJING` | `09:30` | 分析完成后的补发时间门槛；主触发时间仍需同时修改工作流 cron |
| `LLM_OFFPEAK_ONLY` | `true` | `true` 时按配置阻止高峰 API 调用，优先谷时省钱；设为 `false` 改为按时优先；不会自动判断平台价格 |
| `LLM_BILLING_TIMEZONE` | `Asia/Shanghai` | 计费时区；默认北京时间 |
| `LLM_PEAK_WINDOWS` | `09:00-12:00,14:00-18:00` | 同一天的高峰区间，开始包含、结束不包含 |
| `LLM_PEAK_WEEKDAYS` | `1,2,3,4,5` | 哪些星期执行高峰规则，1=周一，7=周日 |
| `LLM_OFFPEAK_HOLIDAYS` | 留空 | 例外低峰日期，格式 `2026-10-01,2026-10-02`；按平台公布日历自行维护 |
| `LLM_PEAK_GUARD_MINUTES` | `10` | 高峰前提前停止启动请求的安全余量 |
| `ARXIV_FRESHNESS_PRIORITY` | `false` | `true`：冬令时北京时间 09:00 起允许上午高峰例外，适合希望上午送达时开启；09:30 前完成则等待，之后完成则补发 |
| `WINTER_PEAK_UNTIL` | `10:30` | 上述例外的结束时间；结束前仍保留安全余量，高峰保护继续生效 |
| `MAX_DIGEST_AGE_HOURS` | `48` | 推送时允许的批次最大年龄，按抓取时间检查；希望只看当天可设 `6` |

高峰窗口示例来自用户提供的计费规则，不是对 DeepSeek 所有模型、接口或中转平台的价格承诺。折扣及计费归属以实际服务商规则为准。未维护节假日时，系统保守地按普通工作日判断；不会擅自把未知日期当优惠日。每次 API 请求及 HTTP 重试都会检查时段；已经开始的请求不会被强行取消，安全余量也不能代替服务商的结算规则。

默认北京时间规则在 Windows 上不需要额外时区包；若本地使用其他 IANA 计费时区但系统缺少时区数据，可安装 Python 的 `tzdata` 包。冬令时例外使用美国自 2007 年以来的夏令时规则；若未来规则变更，需要随之更新实现。

## 来源与开销 Variables

| 变量 | 默认值 | 作用 |
| --- | --- | --- |
| `HF_ENABLED` | `true` | 启用 HF 精选 |
| `HF_LOOKBACK_DAYS` | `3` | 回看天数，1–14 |
| `HF_MIN_UPVOTES` | `0` | 最低社区票数 |
| `HF_MAX_PAPERS` | `20` | 排除已推送论文后的 HF 候选上限 |
| `ARXIV_ENABLED` | `false` | 启用 arXiv RSS 关键词候选 |
| `ARXIV_CATEGORIES` | `cs.AI,cs.CL,cs.LG` | arXiv 分类，用英文逗号分隔 |
| `PAPER_METADATA_ENABLED` | `true` | 额外抓取作者机构和代码链接 |
| `MAX_DETAILED_PAPERS` | `10` | 日报最多展开篇数，1–20；不减少分析数量 |
| `LLM_CONCURRENCY` | `4` | API 并发数，1–16；降低可减少限流 |
| `LLM_MAX_PAPERS` | `100` | 全部来源合并后的分析数量安全上限，超限报错，不静默丢论文 |
| `LLM_TIMEOUT_SECONDS` | `60` | 单次模型请求超时，最大 600 秒；应小于低峰安全余量 |

`PAPER_KEYWORDS`、`PAPER_FOCUS`、`PAPER_PREFERENCES`、`DIGEST_TITLE`、`FEISHU_DOC_ID` 和 `DAILY_ENABLED` 沿用原设置。模型三项与飞书凭据仍放 Secrets，不放 Variables。

## 排错与手动补跑

- `tick`：按北京时间和保存进度执行定时检查，遵守低峰规则；用于手动验证自动决策。
- `check`：只检查配置，不联网分析或推送，可在高峰时段执行。
- `preview`：生成临时预览，照常计模型费用并受时段保护，不进入正式待发状态。
- `analyze`：在允许时段生成待发日报；手动执行只分析，不自动投递。
- `publish`：立即发送已有正式待发日报，不调用模型；没有批次时跳过，批次未完成则报错。
- `all`：立即抓取、分析、发送，受低峰规则保护。

如果模型调用被高峰保护挡住，应等到允许时段重跑 `analyze`，然后再运行 `publish`。不要通过关闭保护来假装享有低价。如果日报超过最大年龄或持续失败，先检查未完成批次再处理；系统宁可停止，也不悄悄发送过期报告。

确需当天例外测试时，可在手动运行中勾选 `allow_peak`。它只允许**本次运行**按实际价格调用模型，不修改仓库 Variables，也不影响后续定时保护。定时事件始终不会启用这个手动例外。

## 日报展示

所有日报日期与公告时间均为北京时间。标题按 `年月日-会议/期刊-一作机构-核心贡献` 生成：年月日为北京时间日报收录日（例如 `26.09.29`），不是论文发表日，会议/期刊只采用明确出版元数据，一作机构取论文作者栏并由 LLM 翻译为简短中文名，学校采用常用简称，Meta、Google 等通用品牌保留英文；缺失部分省略，不使用 `arxiv` 或 `?` 占位。

群卡片使用 Markdown 加粗、链接、分隔线和 🔥 相关性标记。开头展示本批实际总结模型；群消息保留完整中文摘要，后续分析要求约 220–350 字，信息不足时不编造。群内减少单独的证据、局限和阅读建议栏目，完整分析保留在文档中。代码链接仅在发现时展示，链接存在不代表许可证已核验。

低相关默认只列 5 篇标题链接，可用 GitHub Variable `MAX_LOW_PAPERS`（0–20）调整，本地对应 `render.max_low`。该上限不影响候选分析和去重数量。历史已生成摘要不会因为修改提示词自动变长，新批次开始使用新的分析要求。

## 定时未准点时如何处理

GitHub定时事件可能延迟，甚至没有产生运行记录；工作流显示active也不是准点执行保证。先确认Actions里是否有当天运行，再看执行步骤的北京时间和决策日志。缺少分析时，`tick`会在允许计费时段补齐；已有日报时可手动 `publish`，不增加模型费用。高峰受保护时会记录等待低峰，配置错误或流水线失败仍显示失败。若全天都没有触发，代码无法自行唤醒GitHub，需手动运行并检查平台状态。当前仅使用GitHub Actions，多次触发提高恢复机会，但不能承诺09:30绝对送达。

**绿色运行记录不等于论文日报已发送。** 如果已经过推送目标时间，但分析因高峰保护而暂缓，运行会产生黄色警告，明确说明本次没有发送日报。实际送达应检查日志中的 `feishu_bot ok`、`feishu_doc ok` 与批次完成记录；当天无符合条件的论文时，群推送也会跳过。

如果上午的cron直到下午才产生运行，先比较日志中的 `cron` 与实际UTC、北京时间。任务创建晚和runner排队是不同问题；更换时区、增加补查或重新启用工作流都不能证明平台延迟已修复。重新启用后必须观察后续自动事件，不能拿手动运行成功代替定时准点验证。坚持仅使用GitHub时，平台延迟仍可能使推送晚于上午10点。
